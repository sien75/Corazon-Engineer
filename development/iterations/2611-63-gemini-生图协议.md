# 2611-63 gemini 生图协议

## 需求

`image` 工具只会两种请求形状：OpenAI `/images/generations`（`/images/edits`）和
chat-completions 的 image 模态。ZenMux 上的 Gemini 生图模型（Nano Banana 2 / Pro）
两种都不认，只认 Google 的 `generateContent`，所以这些模型能进 `models.json`
但工具调不动。

## 目标

- `image` 工具多一种请求形状：Gemini `generateContent`。
- 形状选择是确定的：provider 自己声明 `api: "google-vertex"` 时先走 Gemini，
  否则维持「images → chat → gemini」的 404/405 兜底链。
- 参考图在这种形状里走 `inlineData`（base64），即编辑语义。

## 非目标

- 不新做 publisher 的网络探测：publisher 由模型 id 的厂商标识映射（见下），不认识的厂商
  自己当 publisher，错了就是 404，不会静默打到别的厂商。
- 不改 `models.yaml` 的语义：`image` 仍然是 `provider/model-id`。
- 不改 pi 的模型目录行为。

## 设计

ZenMux 同一把 key 下，Gemini 生图挂在 Vertex 兼容的 base：
`https://zenmux.ai/api/vertex-ai/v1/publishers/google/models/<model>:generateContent`。
它与 `zenmux-openai` 的 base（`…/api/v1`）不是一个根，所以**新增一个 provider**
`zenmux-vertex`（`api: google-vertex`）承载这两个模型——baseUrl 由 provider 给出，
工具不去猜路径。

形状选择用 provider 声明的 api，而不是靠失败试出来：Vertex 形状的 base 对
`/images/generations` 回 404、对 `/chat/completions` 回 **500**，500 不是「形状不对」
的合法信号（真 500 不该重试），所以必须由声明决定顺序。声明缺失时仍走原来的
404/405 兜底链，浏览器网关行为不变。

**形状 4（Vertex `:predict`）同时做了**：豆包 / FLUX / Qwen 这些 imageOnly 模型在同一个
Vertex base 上只认 `:predict`，与 Gemini 的 `:generateContent` 是同一个网关的两个入口。
于是 provider 声明 `google-vertex` 时按「先 `:generateContent`，404/405 再 `:predict`」试一次
—— 反过来没有任何依据：两个形状对彼此的模型都回 404。

```
POST {baseUrl}/v1/publishers/{publisher}/models/{id}:predict
{"instances":[{"prompt":…}],"parameters":{"sampleCount":n}}
→ predictions[0].bytesBase64Encoded | predictions[0].gcsUri
```

publisher 映射：`bytedance → volcengine`（字节的图像由 volcengine 供），
`google / qwen / bfl / inclusionai` 各自同名，其余用厂商本身。model 名同样去掉厂商前缀。

请求（形状 3，Gemini）：

```
POST {baseUrl}/v1/publishers/google/models/{id}:generateContent
{"contents":[{"role":"user","parts":[{"text":…},{"inlineData":{"mimeType","data"}}]}],
 "generationConfig":{"responseModalities":["TEXT","IMAGE"],"imageConfig":{"aspectRatio"?}}}
→ candidates[0].content.parts[i].inlineData{data,mimeType}
```

- 路径里的 model id 去掉与 publisher 重复的前缀（`google/gemini-3.1-flash-image`
  → `gemini-3.1-flash-image`），实测带前缀是 404。
- `baseUrl` 已以 `/v1` 结尾时不再补 `/v1`。
- `size` 能约成常见宽高比（1:1 / 3:2 / 16:9 …）才发 `imageConfig.aspectRatio`，
  约不出来就不发，让模型用默认比例，而不是四舍五入成另一张图。
- 返回按 `inlineData` / `inline_data` 两种拼写都解析，落 blob 与前两种形状共用。

## 影响面

- `workspace/ai/src/images.ts`：新增第三形状 + `aspectRatio()`；`pickImages()` 解 `candidates`。
- 配置：`~/.pi/agent/models.json` 新增 `zenmux-vertex` provider，Gemini 两个模型搬过去。
- 凭据：`~/.pi/agent/auth.json` 需要一条 `zenmux-vertex` 的 key（用户的凭据，不由 Agent 写）。

## 验收

1. provider 声明 `google-vertex` 时，一次 `image` 调用只打一次网络，落在 `:generateContent`，
   `details.shape === "gemini"`，图落 blob。
2. 声明缺失时（旧 provider），images/chat 各 404 后仍会试 gemini。
3. `openai/gpt-image-2.6-flare` 行为不变（仍走 `/images/generations`）。

已做的验证（真网关、真 key，各一张图，都落 blob）：

| 模型 | 形状 | 结果 |
|---|---|---|
| google/gemini-3.1-flash-image | gemini | 12s |
| google/gemini-3-pro-image | gemini | 21s |
| bytedance/doubao-seedream-5.0-pro | predict | 58s（回 jpeg） |
| bfl/flux-3-image | predict | 23s |
| qwen/qwen-image-3.0 | predict | 86s |
| qwen/qwen-image-3.0-pro | predict | 68s |

E2E 用例：`development/testing/dev/case-core-ai-image-vertex/`。
调用方要带一条 `zenmux-vertex` 凭据（`~/.pi/agent/auth.json`）。
