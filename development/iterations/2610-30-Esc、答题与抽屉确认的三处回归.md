# Esc、答题与抽屉确认的三处回归

> 修 `2610-27`（每个 pane 自己的 composer）与 `2610-29`（pane 共享会话流与格子身份）带出来的三处回归：**Esc 不再停 run**、**ask_user 卡片点了没反应**、**会话选择器里按 `d` 删不掉会话**。都在前端，契约不动。
>
> 第三处不在最初那份报告里 —— 它是写这个用例时撞上的，但必须一并修：删除确认框就是 Esc 分层的**第一层**。

## 需求

用户报告（原话）：

1. **Esc stop chat 不生效了** —— 以前在跑着的 run 上按 Esc 会停下来。
2. **问问题、回答问题的点击不生效** —— agent 用 `ask_user` 提问后，点选项没反应。

要求：这两条回到能用；同一次排查里确认它们与 tab/pane 改动的关系，并把漏掉的回归覆盖补上。

## 现状（改之前）

两处都是 `2610-27` / `2610-29` 那两轮 pane/tab 重构的尾巴：一处是**监听被删没补**，一处是**参数改了/漏了、调用方没跟上**。

### 1. Esc 停止：`b6e5af7` 删掉了 chat 侧的全局 Esc 监听

旧代码有两个全局 `keydown`（`b6e5af7^:app.js:2557` 新建页、`b6e5af7^:app.js:3296` chat）。chat 那个按层退出：

```js
window.addEventListener("keydown", (event) => {
  if (event.key !== "Escape") return;
  if (aiConfirm) { event.preventDefault(); aiConfirmClose(); return; }   // 删除确认
  if (!themeMenuEl.hidden) { event.preventDefault(); themeMenuHide(); return; } // 主题菜单
  if (aiDrawer) { event.preventDefault(); ...aiCancelResume()/aiDrawerHide(); return; } // 抽屉
  if (!aiStreaming) return;
  event.preventDefault();
  aiStop();                                                              // 停止在跑的 run
});
```

`b6e5af7` 把 `aiConfirm` / `aiDrawer` / `aiStreaming` 全部改成 pane 级状态，于是**整个监听被删掉，没有替代品**（`aiConfirmDelete` 的注释还写着 "Esc (handled globally)"，`app.js:3491`）。现在只剩 `app.js:3353` 那个只管新建页的监听，条件还是 `newTabOpen`：

```js
if (event.key === "Escape" && newTabOpen) { ... }
```

所以丢的不只是"停 run"：**删会话确认框、主题菜单、命令/历史抽屉的 Esc 也一起没了**。`aiStop()` 本身没坏 —— stop 按钮那条路径（`bindComposer` → `composerOn(pane.stopEl, "click", ...)`）一直是通的。

### 2. ask_user 答题：`a99d3e9` 漏了一个参数，又改漏了 `aiAnswer` 的签名

这一处有两个 bug 叠在一起，第一个是根因：

**（a）`aiHandleOne` 上没有 `hub`。** 同一提交把渲染循环改成按 target 走，并在 `tool_execution_start` 里加了

```js
function aiHandleOne(t, ev) {            // app.js:2076 —— 形参里没有 hub
  ...
  if (ev.toolName === "ask_user") {
    const card = aiAskUser(ev.args, (value) => aiHubAnswer(hub, value));
    hub.cards.set(pane, card.disable);   // ← ReferenceError: hub is not defined
  }
```

`aiAskUser(...)` 先跑完（箭头函数体里的 `hub` 是延迟求值，建卡片时不报），紧接着 `hub.cards.set(...)` **当场抛 `ReferenceError`**。这个异常从 `aiHandleOne` 一路冒到 `aiRunStream` 的 `catch`，被当成一次“连接掉线”：重连 → `aiHubRederive` 拿到 `lastSeq` 已经越过这条事件 → **剩下的事件被水位过滤掉，run 就此卡死**。

实测（fixture 位一个 `ask_user`，会话挂在两块 pane 上）：`hub.targets = [p_a, p_b]`，但 `aiHandleOne` 只在 `p_a` 上跑完了；`p_b` 什么都没拿到，而且它 `p_a` 手上也只多一张卡、不会继续。这正是“点了不生效”的现场 —— 另一块 pane 连问题都看不到。

**（b）`aiAnswer` 的签名改了，调用方没改。** 同一提交把 `aiAnswer` 从 1 参变 3 参：

```js
async function aiAnswer(hub, pane, answer) { ... }   // app.js:2288
```

但 `aiHubAnswer` 还是旧的 2 参调用（而且即使 `hub` 在作用域里也会抛，见上）：

```js
function aiHubAnswer(hub, value) {
  for (const disable of [...hub.cards.values()]) disable();
  hub.cards.clear();
  void aiAnswer(hub, value);        // ← value 落进 pane，answer 是 undefined
}
```

于是：`pane` = 选项值（字符串），`answer` = `undefined`。请求体实测（`node -e 'yaml.dump({...text: undefined})'`）没有 `text` 字段 → 服务端 `workspace/ai/src/server.ts:110` 把这个 block 过滤掉 → `blocks.length === 0` → **400 `blocks required`**。`tabId` 同时丢：`tabTalkId(sender)` 对字符串走 `tabOfPane` 找不到 tab，返回 `""`，`layout` 工具这一轮没有目标。

**合起来表现为“点了不生效”**：`aiAskUser` 的 `done()` 先 `disable()` 再 `onPick()`，卡片当场被禁用（再点也没反应），而 `onPick` 里那句 `aiHubAnswer(hub, ...)` 自己就没法求值。即使侥幸修好了它，请求也是缺 `text` 的 400。

### 3. 删除确认：`b6e5af7` 把调用改成了 `pane.confirmDelete`，而它从来没有被定义过

写这个用例的过程中找到的第三处（同一族）：会话选择器里按 `d` 删会话，调用的是

```js
pane.confirmDelete(pane.drawer.items[pane.drawer.index]);   // app.js:4142
```

而 `pane.confirmDelete` 在整个文件里**只出现在这一处**（`grep -n confirmDelete app.js`）—— 改成了 pane 级方法却没把方法写下。按下去就是一个 TypeError，确认框永远不弹（`aiConfirmDelete` 本身是写好的，只是没人叫它）。

这处必须一并修：确认框是 Esc 分层的**第一层**，不修就没法验证它。


### 为什么没有用例挡住

- `grep -n "ai-question\|question-options" development/testing/dev/*/TEST.md` → 无命中：**没有用例点过 ask_user 卡片**（`case-core-web-tool-chips` 只断言它在**历史回放**里不变 chip，那条路径不过 `aiHandleOne`）。
- `grep -rn Escape development/testing/dev/` → 只有 `case-core-web-chat-route`（Esc 退新建页）与 `case-core-web-input-history`：**没有用例在 run 在飞时按 Esc 验证 `/ai/stop`**。

（a）意味着要测出它，必须让 `ask_user` 事件真的走一遍 `aiHandleOne` —— 真模型问不出来，所以只能靠 fixture 喂事件流；第三处同理，没有用例在会话选择器里按过 `d`（`grep -rn '"d"' development/testing/dev/` 无命中）。缺口不是“测不了”，是“没测”。

这三处里有**两处是靠“异常被吞掉”活着的**：`aiHandleOne` 的 `ReferenceError` 被 `aiRunStream` 当成掉线重连，`aiCmdKeydown` 的 `TypeError` 直接进 window 的错误通道无人看 —— 都不报错、都不崩页，只是不干事。同一个形状的 dangle 值得再扫一遍（本次 `grep` 了 `pane.*` 的全部成员，只剩这一处）。

## 决策

1. **恢复 chat 侧的全局 Esc，但升到 pane 级语义**：不再看 `aiStreaming` 这个单例，而是**当前 pane（`aiPane`）所在会话的 hub** 是否在跑。分层顺序沿用旧的：确认框 → 主题菜单 → 抽屉 → 停 run。
2. **新建页的 Esc 优先，而且写成同一个监听**：launcher 打开时 chat 侧直接返回，不抢。**两个监听各写一份是错的** —— 先跑的那个（launcher）会把 `newTabOpen` 置 false，后跑的 chat 那层于是不再认为自己该让位，结果是“关掉 launcher 的那次 Esc 顺手把后面的 run 也停了”。顺序得是代码写死的，不能靠注册先后。
3. **不在 composer 的 `keydown` 里处理 Esc**：焦点可能在抽屉、确认按钮、主题菜单上，全局监听才是唯一能覆盖全部的地方（旧实现也是全局）。
4. **`aiHubAnswer` / `aiHandleOne` 显式接 `hub` 与 `pane`**：`aiHandleOne` 需要 hub（`hub.cards` 是“一块提问、处处收起”的宿主），所以从 `aiHandleEvent` 传进去；卡片是在 `aiHandleOne` 里、按 pane（target）建的，闭包里就有 `pane`，把它一路带到 `aiAnswer`。不改成 `hub.sender` —— 答题要替**你作答所在的那个 tab** 说话（`layout` 工具的目标），而 `hub.sender` 是发起 run 的那一格；被丢掉的 pane 上的卡片不在文档里、点不到，所以不需要额外兜底。
5. **不动契约与静态关系**：`/ai/ask`、`/ai/stop` 的形状本来就够用（`ai-ask.yaml` 说答题就是普通 text block），这次是实现没按契约调用。
6. **补一个能覆盖三处的浏览器用例**：用 fixture 喂事件流（同 `case-core-web-tool-chips` / `case-core-web-pane-frame` 的做法），这样 run 停在"提问中"、@Esc 时有确定的在飞 run，都不依赖真模型。

## 方案

### `workspace/web/app.js`

**Esc 分层**（把原来只管 launcher 的监听扩成一个，依次处理）：

```js
window.addEventListener("keydown", (event) => {
  if (event.key !== "Escape") return;
  if (newTabOpen) {            // 最外层：launcher
    event.preventDefault();
    if (newTabMode !== "home") newTabGo("home", "replace");
    else closeNewTab();
    return;
  }
  if (aiPane?.confirm) { event.preventDefault(); aiConfirmClose(); return; }
  if (!themeMenuEl.hidden) { event.preventDefault(); themeMenuHide(); return; }
  if (aiPane?.drawer) {
    event.preventDefault();
    if (aiPane.drawer.kind === "session") aiCancelResume();
    else aiDrawerHide();
    return;
  }
  const hub = aiPane?.session ? aiHubs.get(aiPane.session) : null;
  if (!hub?.streaming) return;
  event.preventDefault();
  aiStop();
});
```

**删除确认回到真正实现它的那个函数**：

```js
// aiCmdKeydown —— pane.confirmDelete 从未定义过
aiConfirmDelete(pane.drawer.items[pane.drawer.index]);
```

**答题传参 + 补上 `hub`**：

```js
// aiHandleEvent
for (const t of [...hub.targets]) aiHandleOne(hub, t, ev);

// aiHandleOne, tool_execution_start
const card = aiAskUser(ev.args, (value) => aiHubAnswer(hub, pane, value));

function aiHubAnswer(hub, pane, value) {
  for (const disable of [...hub.cards.values()]) disable();
  hub.cards.clear();
  void aiAnswer(hub, pane, value);
}
```

顺手修 `aiConfirmDelete` 上那句过期注释（"Esc (handled globally)" 现在真的成立了，但把处理者说清楚）。

### 不用改

- `contracts/`、`atoms/` `edges/`：两处都是实现偏离既有契约，没有新接口、没有新依赖。
- `workspace/ai/`：服务端行为正确（缺 `text` 就该 400），不该为了迁就前端放宽。
- `docs/`、`README`：全文没有 Esc 的说明（`grep -rn "Esc\|Escape" --include="*.md"` 只命中测试用例与迭代记录），无漂移可修。

## 测试

新增 `development/testing/dev/case-core-web-chat-controls/`（端口块 9010/9011，fixture 用 Go 自陈的假 provider，同 `case-core-web-pane-frame`）。四段顺序有讲究：**答题段必须排在停 run 段之前** —— 被 Esc 停掉的那个问题，卡片会一直留在屏幕上（卡片只在“被作答”时收起），先跑停 run 会让后面“启用中的选项数”的断言多算一张卡。

1. **答题往返**：脚本喂 `tool_execution_start(ask_user)` 后**保持 SSE 连接开着**（run 在飞），断言**两块 pane 都出现卡片**（这一条就是 `hub` 那个 ReferenceError 的现场）；点选项 → 断言 fixture 收到的 `/ai/ask` 里 `text` 是选项值、`tabId` 非空；fixture 随即在同一条流里推 `text_delta` + `agent_settled` → 断言界面出现该串文本、两块 pane 的卡片一起禁用。
2. **Esc 停 run**：run 在飞（stop 按钮可见）时按 Esc → 断言 fixture 收到 `/ai/stop`，且 stop 按钮消失。
3. **Esc 分层**：`/resume` 抽屉开着时 Esc 关抽屉；删除确认框开着时 Esc 只关确认框（抽屉还在）；主题菜单开着时 Esc 关菜单。
4. **反向守卫**：launcher 打开时按 Esc 走新建页逻辑，不触发 `/ai/stop`（后面那个 run 还在飞）；紧接着断言那个 run 仍在飞（stop 控件还在）。

fixture 要注意两条“别比真实服务更极端”的地方：

- **事件要等 `/ai/ask` 返回后再发**（`go func(){ time.Sleep(150ms); emit(...) }()`）。真实服务是先回响应、run 随后才流；fixture 同步 emit 会跑在 `aiHubAttach` 前面，把一个即使 settle 也看不见的次序当成常态。
- **同一会话的事件日志会跨页面累积**，而新建 tab 的 `hub.seenSeq` 是 0：重跑用例前必须先跑 Setup（`pkill` 掉旧 fixture），否则第一条流会把上一轮的 `agent_settled` 重放出来、把流提前关掉。这也是这个用例的 Setup 里 reclaim 那一步存在的理由。

`case-core-web-tool-chips` 的 fixture 里 `ask_user` 只作为“不变 chip”的样本（走历史回放，不过 `aiHandleOne`），不受影响，已一并回归。

## 实测（Phase 3）

- `case-core-web-chat-controls`（新增）：**ok: true，22/22 通过**。
- 回归：`case-core-web-chat-route`（Esc + launcher）、`case-core-web-input-history`（抽屉 + Esc）、`case-core-web-tool-chips`（`ask_user` 不落 chip + 发送路径）→ 三个都 **rc=0，无 fail**。
- 没跑（理由）：`panes` / `pane-frame`（只读 pane 树、flex 与流共享，本次没改）、`chat-scroll` / `input-grow` / `tabs` / `tab-records` / `page` / `serve`，以及全部 ai / log / static 用例（契约与服务端零改动）。
- `static validate` → `ok: true`（无 schema 改动，跑一遍作验收）。

## 验收

- 跑着的 run 上按 Esc → run 停下（stop 按钮消失、`/ai/stop` 被调用）；launcher 开着时 Esc 仍只做新建页的事。
- Esc 仍能逐层退出删除确认 / 主题菜单 / 命令抽屉（与重构前一致）。
- `ask_user` 提问后：**显示这个会话的每一块 pane 都出现卡片**，没有 `ReferenceError`、流不断；点选项（或输入框回答）后请求带正确答案文本与 `tabId`，run 继续，两格的卡片一起收起。
- 新增用例 `ok: true`；`static validate` ok。

## 未采纳 / 待定

- **把 Esc 做成可配置的快捷键**：不必要，先恢复既有行为。
- **让 Esc 停下“所有在跑的会话”**（多 tab 同时跑时）：不采纳。Esc 是“当前 pane 的当前 run”，与 stop 按钮同语义；跨会话打断应该显式点对应的停止键。
- **用例覆盖“两个 pane 各自一块 ask_user 卡片、点一处两处都收”**：本用例已经盖住（fixture 的树就是同一会话挂两块 pane，断言两块都出现卡片、点一处两块都禁用）。
- **“错了就静默重连”这条路径**：排查中发现 `aiHandleOne` 的异常被当成掉线吞掉了 —— 它让一个明显的 JS 错误看起来像“界面卡住”。是否要在事件回调层把渲染异常和传输异常分开（渲染异常应直接报错、不重连），值得单独一轮讨论，本期不动。
- **`aiSend` / `aiAnswer` 里“先 await、再 `aiHubAttach(running=true)`”这个次序**：若 run 在前端 attach 之前就 settle（真实服务里第一轮几乎不可能 —— 事件总晚于响应；中途 steer 且服务端立刻出错时理论上可以），会留下“没有 run 在跑、stop 键却亮着”的状态。fixture 已刻意避开这个次序，但它本身是个真 bug，值得单独一轮。
