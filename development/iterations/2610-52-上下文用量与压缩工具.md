# 上下文用量与压缩：两个工具，不是页面控件

## 需求

「就把用量和压缩做了吧，都是 tool，也都是通过对应的用户发消息触发，不是斜杠命令，在页面上没有入口。」

即：pi 已有 `getContextUsage()` / `getSessionStats()` / `compact()`，把这三样透上来给**模型**调，
用户用自己的话触发（「上下文还剩多少」「压缩一下」），页面上不加任何按钮。

范围外：模型的人侧入口与持久化（上一轮已定：不做；`model` 工具已存在，切换不落库）、fork、
thinking 档位设置、provider 登录入口。

## 现状（实测）

- `workspace/ai/src/` 只有 `model.ts` 一个"会话能力"工具；`usage` / `compact` 没有任何调用点
  （`grep getContextUsage|compact` 只命中 `recorder.ts` 的注释和 `registry.ts` 的 compaction 回放）。
- 记录侧已经齐了：`registry.ts` 订阅 `compaction_end` → `recordCompaction()`，`toAgentMessage`
  把 `role: "compaction"` 还原成 pi 的 `compactionSummary`，`lastCompactionIndex` 决定回放切片。
  所以压缩**不需要新的持久化代码**。
- 事件侧也齐了：`compaction_start` / `compaction_end` 走原生事件透传（`append(sess, ev)`），
  前端 `chat.js` 里 `compaction` 出现 0 次 —— 压缩发生时用户看不到任何提示，本轮不改前端。

## 关键约束：`compact()` 不能在工具里直接调

pi 的实现（`dist/core/agent-session.js:1468`）：

```js
async compact(customInstructions) {
    await this.abort();          // 先中止在跑的一轮
    await this.waitForIdle();    // 再等空闲
    ...
}
```

工具是在**正在跑的那一轮**里执行的。若在 `execute` 里 `await agent.compact()`，它会等这一轮空闲，
而这一轮正卡在这个工具上 → **死锁**。所以工具只做"登记"，不做事：

```ts
deps.schedule(async () => { await agent.compact(instructions); });
```

`schedule` 由 registry 提供，落到本会话的 `sess.tail` 上：

```ts
schedule: (run) => {
  sess.tail = sess.tail.then(run).catch((err) => {
    dbg(sess.id, "compact error", String(err));
    this.appendError(sess, "compact_error", String(err));
  });
},
```

`ask()` 在空闲时也是往 `sess.tail` 上挂 `runTurn`，所以顺序天然是
**这一轮 → 压缩 → 下一轮**；压缩时 agent 已空闲，`abort()` 是空操作。
`compaction_end` 事件走同一条订阅，摘要照常落 log。

## 方案

新增两个文件，各一个工具，都按 `model.ts` 的形状（`defineTool` + deps 注入，不碰 registry 内部）：

**`workspace/ai/src/usage.ts` — `usage`（只读）**

无参数。输出一段可读文本 + `details`：

- `model: provider/id (thinking <level>)`
- `context: 12.3k / 128k tokens (9.6%), 115.7k left`；`tokens === null`（刚压缩完）时写明
  "下一轮回复后才有数"
- `conversation: N messages (a user, b assistant, c tool calls)` — `getSessionStats()`
- `billed: in …, out …, total …`，有 cache 时分列 cache read / write
- `cost: $0.0432`
- `compactions: n on this branch, the latest summarized X tokens` — 数
  `sessionManager.getBranch()` 里的 `type === "compaction"` 条目

任何一步读不到都不让整个调用失败：`getContextUsage()` 为 undefined 时退回 `stats.contextUsage`，
再没有就写 "unknown"；`getBranch()` 抛错就跳过压缩统计。

**`workspace/ai/src/compact.ts` — `compact`**

可选参数 `instructions`（摘要必须保留什么）。行为：

- 无 agent（stub）→ 失败。
- 已有一个排着（模块内 `scheduled` 标志）→ 失败，说明"已经排了，本轮结束后执行"。
- 否则登记到 tail，立刻返回：说明本轮回复不受影响、压缩在本轮结束后执行、下一轮从摘要开始。

工具描述里写清 **pi 自己会在接近上限时自动压缩**，只在用户要求时调用 —— 否则模型会自作主张
把上下文截了。

**接线（`registry.ts`）**

- `tools: [...]` 白名单加 `"usage"`、`"compact"`（pi 的 allowlist 按名字，漏了就调不到）。
- `customTools: [...]` 加两个实例，`getAgent: () => sess.agent`（与 `model` 一致，懒取，因为
  `sess.agent` 在 `createAgentSession` 返回后才赋值）。
- main 与 sub 都有：用量和压缩是每条对话自己的事，不属于工作区。

**文档**

`atoms/ai.yaml` 的工具描述、`agents/{main,sub}/AGENTS.md` 与 `agents/zh/**` 的工具清单同步。

## 影响面与验收

契约、log schema、web 页面都不改：工具调用本身就是 `tool_execution_*` 事件，已有的透传与
`chat.js` 的 tool chip 已经覆盖；压缩的摘要走已有的 `compaction` 记录。

验收（dev 栈 8500 段，真实模型）：

1. 一句"上下文还剩多少" → `tool_execution_start {toolName: "usage"}`，结果里出现
   `context: … / … tokens`、`billed:`、`compactions:`。
2. 一句"压缩一下上下文" → `tool_execution_start {toolName: "compact"}`，本轮正常收尾，
   随后流里出现 `compaction_start` / `compaction_end`，log 里多一条 `role: "compaction"` 记录。
3. 压缩后再问一次用量 → `context` 明显变小、`compactions: 1`。
4. 刷新页面 → 历史照常回放（压缩摘要已在记录里）。

## 实跑结果（2026-10-27，dev 8500–8503，deepseek/deepseek-flash）

1. **usage 生效**：`tool_execution_start/end {toolName: usage}`，结果
   `context: 8.9k / 1.00M tokens (0.9%), 991.08k left`、`conversation: 2 messages`、
   `billed: in 8.9k, out 21, total 8.9k`、`cost: $0.0000`、`compactions: none yet on this branch`。
2. **compact 先报错后成功**。小会话直接调用 → `compaction_end.errorMessage`
   = `Nothing to compact (session too small)`，并被包装成 `compact_error` 事件（见"实跑发现的
   两处修正"第 1 条）。把四个源文件全文读进上下文后（约 86k）再调 → 本轮照常收尾
   （`agent_settled` 在 `compaction_start` 之前）→ `compaction_end` 带真实摘要，log 新增一条
   `role: "compaction"`（`tokensBefore: 55.5k`）。
3. **压缩后用量变小**：39 条消息、上下文 31.3k（摘要 + 保留的 ~20k 近期），`compactions: 1`。
4. **重启 + resume 仍然成立**：重启整个栈 → `POST /ai/resume` → 问 usage →
   `context: 11.6k / 1.00M`、`compactions: 1 on this branch, the latest summarized 55.5k tokens`。
   这一条正是下面第 2 处修正的来源。

未跑的用例：`case-core-ai-flow` 与 `case-core-ai-recover` 本轮没跑。两者断言的是记录形状、
事件序列、ask_user 与 compaction 回放切片，本轮一行没改；新增的是两个工具的注册与白名单，
而工具调用本身走的是既有的 `tool_execution_*` 透传。上一轮 `model` 工具入库时按同样口径
只跑了 `case-core-ai-flow` §1/§2/§3/§5，本轮沿用它并补了上面四项手测。前端未改：
`chat.js` 的 `toolChip(name, args)` 对工具名无白名单，两个新工具自带 chip。

## 设计上顺手定下的两点

1. **压缩失败也要说清楚**。`schedule` 里 `compact()` 抛错时若只 `dbg`，用户只会看到
   `compaction_end.errorMessage`，而那条事件在前端没有渲染（`chat.js` 里 `compaction` 出现 0 次）。
   所以 registry 的 `schedule` 捕获后追加一条 `compact_error` 事件（复用已有 error 形状），
   用户至少能在对话里看到原因。
2. **重启后别谎称没压缩过**。live 会话里压缩是 `type: "compaction"` 的条目，而 resume 时
   registry 把记录还原成 `appendMessage({role: "compactionSummary"})` —— 只数前者的实现会在
   重启后报 `compactions: none`。`usage` 改为两种形状都数（条目或消息），实测重启后仍是 1。

## 不做的事

- 不给页面加入口（用户明确要求）；不做 `usage` 的流字段。
- 压缩失败不自动重试：`compact()` 是用户显式动作，失败原因原样交给用户。

## 追加（同日）：压缩要当场看得见

用户看完第一版后提的：“压缩要像 thinking 或者 tooluse 那样展示一下，不要下次用户再发消息再触发。”
不是要改触发时机——压缩本来就是这一轮一结束就跑，是**看不见**：

1. **流在 compression 之前就关了**。`server.ts` 的 SSE 遇到 `agent_settled` 就关流，而手动压缩排在
   agent_settled 之后（`compact.ts` 的 tail 设计）—— 于是 `compaction_start/end` 发给了已关的流，
   用户只能在下一次发消息、新流回放 backlog 时才“突然”看到。
2. **页面根本不画 compression**。`chat.js` 里 `compaction` 出现 0 次。

**改法（三层都动，都在已定范围内）**

- `Sess.compacting`：`compact` 工具排上队时置 true，`compaction_end` 清 false（schedule 的 `finally` 兼底）。
- `server.ts` 关流条件变成：`compaction_end && !sess.active` 关；`agent_settled && !compacting` 关；
  挂载时的“已追平就关”也加上 `!compacting`。压缩是唯一发生在收工之后的事，流为它多开这几秒。
- `chat.js`：
  - `compaction_start` → 建一个与 thinking 同款的芯片（转圈），`compaction_end` 落定：
    成功填“因何触发 / 压缩前多少 token / 摘要正文”，失败显示 `!` 和 pi 的原话。
  - 重放：`raw.role === "compaction"` 的记录也画成同一个芯片（已落定），刷新后依旧看得到。
  - `expectCompact`：`compact` 工具调用成功后，收到 `agent_settled` **不收工**（否则芯片被当旧块、跑还挂着），
    等 `compaction_end`；`finish()` 兼容：没等到就收工时把芯片落定，不让它永远转圈。
  - 压缩期间再发一条：服务端会把那一轮挂在压缩后面（`agent.isStreaming` 为假），流也不关；
    客户端 `compaction_end` 后先问一次 `resumeState()`，还有 Activity 就不收工。

**实跑（ego-browser，dev 8500，deepseek-flash）**

1. 刷新页面：重放里出现一个 `compaction` 芯片，夹在 `compact` 工具芯片和后续 `usage` 之间，
   展开读到 `trigger: manual compaction / context before: 55.5k tokens / ## Goal …`。
2. 在页面上说“压缩一下”：小上下文时 → 芯片先出现、随后 `!`（`Nothing to compact (session too small)`），
   期间 stop 一直亮着（收工等到了压缩结束）。
3. 灌满上下文（四个文件，约 43k）后再说“压缩”：**同一个流里**芯片先转圈，随即落定
   为 `compaction · 43.3k tokens ✓`，展开是 `trigger: manual compaction / context before: 43.3k tokens / 摘要`。
   不需要下一条消息。

**本轮不动**：独立页面里芯片展开的面板看不到（`.ai-chip-group` 没有 `open` 类，CSS 把组内面板
只当隐藏）。用普通 tool 芯片对照实浏：同样 `display: none`。这是页面级的旧现状，与本次改动无关，
确认压缩芯片与 tool 芯片表现一致后未改。

## 被动压缩（threshold / overflow）同不同

同一对事件、同一段渲染代码：`compaction_start` / `compaction_end` 不分手动与自动，
芯片上唯一区别是 `trigger:` 那一行写的是 `manual` 还是 `threshold` / `overflow`。
事件顺序上天生的差别也不影响：被动压缩发生在**一轮内**（下一句助手回复之前，或者 overflow 重试前），
那时 `sess.active` 为真 —— 服务端不关流，客户端也不会在 `compaction_end` 后看 `resumeState()`
就收工（那里仅 `!st.active` 才收）。

**实跑（自动触发）**：临时把 pi 的压缩阈值调小（`PI_CODING_AGENT_DIR=/tmp/pi-auto`，
`reserveTokens: 999000`、`keepRecentTokens: 2000`，`auth.json` 用软链而不是复制凭据），
在页面上 read 三个文件把上下文抬到约 39k，再发一句普通提问 ——
read 那一轮的**中途**出现 `compaction · 39k tokens ✓`，展开为 `trigger: threshold compaction /
context before: 39k tokens / 摘要`，该轮之后助手照常继续回答，log 也新增 `role: compaction`。
验证完删掉临时目录、不带该环境变量重启，进程内已无 `PI_CODING_AGENT_DIR`。

**没验到的一条**：overflow 压缩（`willRetry: true`，上下文超窗口后压缩再重试那一轮）需要真的把
模型撑爆，没构造。它走的是同一对事件、同一个芯片分支，只是给 `willRetry` 多一个真值。

**一个真实差异（不是 bug，但得知道）**：没东西可压时两者表现不一样 ——
`_runAutoCompaction` 在 `prepareCompaction` 返回 undefined 时**直接 return，一个事件都不发**
（页面于是什么都不显示，这是对的）；而 `AgentSession.compact()` 是**先发 compaction_start 再 prepare**，
所以手动压缩没东西可压会以 `compaction_end.errorMessage` → `compact_error` 呈现为芯片 `!`。

## 再追加：摘要当正文展示

用户：“压缩完成后显示个摘要呗，这个摘要正常展示出来。” 之前摘要在芯片的展开面板里，
而那个面板在本页根本不展开（组的 `open` 类没人加）—— 等于没给看。

改法：**摘要不再折进芯片**。`compaction_end` 成功后（以及重放遇到 `role: compaction` 记录时），
在芯片后面插一条 `ai-compaction-summary` 消息：`context summary` 小标 + markdown 正文
（复用 `renderMarkdown`，与助手回复同一渲染器）。芯片自己的展开内容只剩
`trigger` / `context before`，两处不重复。

CSS：`.ai-compaction-summary` 左侧 2px 竖线、`--fg-dim` 13px、标签大写等宽——
读起来是正文而不是某人的发言。

**实跑**：刷新后三个历史压缩各自一条摘要正文（h2 / ul / code 都正常渲染）；
在页面上 read 两个文件再 compact：本轮 stop 亮着，结束后第 4 条摘要立即出现在芯片下方，
不用再发消息。

**待商权**：pi 的摘要有时候很长（本会话那条就含 Goal / Constraints / Progress / Next Steps /
Critical Context 全节）。现在是一律全展开。想要更紧凑可以再加“默认折叠成前几行”，
但那与“正常展示”的要求相反，所以没先说。
