# 切换 tab 保住现场（pane 树不搬家）

> 收 `2610-24`「范围外」里"重排时保住 chat 的滚动位置 / iframe 的现场"这笔欠账。切 tab 走的是同一条"搬树"路径，所以这一条同时修掉两个症状。

## 需求

- 在一个 tab 里把对话读到中间，切走再切回，滚动位置还在原处（现在是回到顶部）。
- page pane 的 iframe 切走再切回**不重载**：页内滚动、表单、页面自己的 JS 状态都不丢。
- 顺带：离开时正在追底的 pane，回来时仍然追底（流在后台照旧继续画）。

## 现状

`showPanes` 是**搬树**：

```js
function showPanes(tab) {
  if (!tab.paneEl) renderPanes(tab);
  panesEl.replaceChildren(tab.paneEl);   // app.js:982-985，上一个 tab 的整棵树被摘出文档
}
```

浏览器的两条事实（`ego-browser` / Chromium 152，实测）：

| 操作 | 结果 |
|---|---|
| 滚动元素滚到 1500 → `removeChild` → `scrollTop` | 立刻 **0**，再插回也是 0 |
| 滚动元素滚到 1500 → `display:none` → 显示回来 | **1500** |
| `display:none` 期间写 `el.scrollTop = el.scrollHeight`（此时读到 0） | 回来仍是 **1500**（隐藏期间的写不覆盖它） |
| iframe 里的页面 → 摘除再插回 | **重新加载**（loads 1→2），页内 `scrollY` 900→0 |
| iframe 里的页面 → `display:none` → 显示回来 | loads 仍 **1**，页内 `scrollY` 仍 **900** |

真实应用里同样成立：聊天 `scrollTop` 1500 → 切走切回 **0**（消息条数不变，只是位置回到顶）；page pane 切走切回 loads **1→2**、页内 `scrollY` **900→0**。

承重处：`focusPane` 把 `#ai-scroll` / `#ai-messages` / `#ai-input` / `#ai-input-field` / `#ai-cmd` / `#ai-send` / `#ai-stop` 借给**聚焦的 pane**，`style.css` 正是按这些 id 上色的（709 / 1082 / 1270 / 1304）。它的清 id 循环只遍历**当前 tab** 的 pane，所以"文档里同一时刻只有一棵树"是这套 id 方案成立的前提。这也正是当初选"搬走"的隐含代价。

## 决策

1. **树不搬家。** 一棵 `pane-tree` 挂进 `#panes` 之后就一直在文档里；切 tab 只切 `hidden`。DOM 本身就是现场，不再写任何"保存/恢复"的簿记。
2. **id 唯一由 `focusPane` 保证。** 清/设 id 的循环从"当前 tab 的 pane"扩到"所有 open tab 的 pane"——`aiPane` 是全局单例，所以"on = p === aiPane"天然只点亮一棵树。这样不再需要"文档里只有一棵树"这条约定。
3. **生命周期跟着树走。** `renderPanes` 换树时先摘掉旧树（`tab.paneEl?.remove()`）；`closeTab` 关 tab 时连树一起摘。失活 tab 的树本来就已经留在内存里（`tab.panes` / 消息 DOM / iframe 都不释放），这里只是把"脱离文档"换成"隐藏"，内存几乎不变。
4. **追底跟着人走。** 隐藏一棵树之前，把它的 chat pane 的"在不在底"记进 `pane.stick`（那一刻还有布局，是最后一次可信读数）；重新显示时，`stick` 的 pane 滚到底。正在读历史（不追底）的 pane 则保留原位置。
5. **CSS 一行**：`.pane-tree[hidden] { display: none }`。作者样式 `.pane-tree { display: flex }`（style.css:572）会盖掉 UA 的 `[hidden]`，必须显式写。
6. **`paneScrollToBottom` 不动。** 隐藏期间的写是 0，实测不覆盖保存的位置，所以在"追底"路径上不需要额外加"有没有布局"的判断。

## 方案

### web（`workspace/web/`）

| 位置 | 改动 |
|---|---|
| `app.js` `showPanes` | 挂一次、切 `hidden`、隐藏前记 `stick`、显示后追底 |

| `app.js` `makeChatPane` | pane 加 `stick: true`（新 pane 默认追底） |
| `app.js` `renderPanes` | 换树前摘掉旧树 |
| `app.js` `closeTab` | 关 tab 时摘掉树 |
| `style.css` | `.pane-tree[hidden]` |

### 契约与静态关系

- 无。纯前端行为，不碰任何接口 / 契约 / atoms / edges。

### 测试

- 新增 `case-core-web-tab-state`（端口 8840-8843）：切走切回，聊天滚动位置还在、正在追底的 pane 回到最新、page pane 的 iframe 没重载且页内位置还在、借出去的 id 仍然唯一。
- 现有 case 里"按 `#panes` 里的节点数断言"的地方要收窄到**可见的那棵树**（`#panes .pane-tree:not([hidden])`）——失活 tab 的树现在也在文档里。

## 范围外

- **布局重排仍会重建容器**（模型改树 → `renderPanes` 造新树 → pane 被搬一次 → 滚动位置与 iframe 现场仍丢）。那是 `2610-24` 的另一笔，且"重排"和"切 tab"是两种不同的意图，另开一条。
- 不做 tab 树的懒挂载 / 卸载（现在也不是：失活 tab 的树一直都留在内存里）。
- 不碰 `#panes` 之外的多树共存（固定视图本来就用 `panesEl.hidden`，同构）。

`aiChipRow` 那一行是被本次改动**暴露出来的真 bug**：旧代码靠 `isConnected` 判断"行还在"，因为那时失活 tab 的树已被摘出文档；树留下来之后，另一个 pane 的 chip 行仍然 connected，历史重放的 chips 就被画进了 tab 页里那个 pane 的行上（`case-core-web-tool-chips` 复现：新 pane 只拿到 `testing`，`registry.ts` 那行跑去了另一个 pane）。

### 顺手修掉的两个既有缺陷

都不是本次改动引入的（基线同样失败，已做 stash 对比），但都挡在本次改动的验收路上：

1. **`aiHubRegister` 重放调错参数**：`aiHandleOne(target, ev)` 少传 `hub` → `ev` 为 `undefined` → 中途加入的 pane 一进来就抛 `Cannot read properties of undefined (reading 'type')`。
   `case-core-web-pane-frame` 3 项失败（基线同样 3 项失败）。修成 `aiHandleOne(hub, target, ev)` 后 12/12。
2. **`primaryPane` 不归一化**：从 log 读回的旧格式记录（`pane.content/id`）被直接当新格式读 → `contentId` 为 `undefined` → 从 `recent` 重开旧 tab 会开出 `sessionId: undefined`（URL `/chat/undefined`）。旧行为只留一棵树，历史正好落进那个新建 pane，把这个缺陷盖住了；树留下来之后才现形。
   `normalizeTree` 挪进 `primaryPane`；`applyPaneLayout` 里读的 `content/id` 一并改成 `contentType/contentId`。
