# 输入框插话、Esc 停止与上下键历史

> 修 `84d52d0`（Every pane mounts `<engineer-chat>`）带出来的三处交互丢失：**run 在飞时发不出消息**、**Esc 停不了 run**、**↑/↓ 翻不到历史提问**。三处都在 `workspace/web/components/chat.js` 一个文件里，契约、atoms、edges 都不动；后端一直支持。

## 需求

用户报告（原话）：

1. 为什么执行中现在无法发送消息了？
2. 为什么按上下箭头键无法恢复历史提问了？
3. 为什么按 esc 也不能 stop 对话呢？

要求：三条都回到能用，`components/chat.js` 里的行为与用户过去的习惯一致（执行中发送 = 插话，不是排队；Esc = 停当前 run，等同 stop 按钮；↑/↓ = 翻本会话发过的提问，含草稿回填与多行规则）。

## 现状（改之前）

三个功能都是**前端搬家的遗漏**：`84d52d0` 把聊天界面从 `workspace/web/app.js` 搬进自建组件 `components/chat.js`，搬了骨架（ask / stream / 渲染 / stop 按钮 / 图片粘贴 / 问题卡），这三件没搬，旧实现随 `app.js` 那一段一起删掉了。后端一行没缺。

### 1. 执行中发送：被前端挡住，后端一直能插话

`components/chat.js` 三处直接挡：

- `ask()`：`if (!blocks.length || running) return;`（`chat.js:483`）
- `submit()`：`if ((!text.trim() && !images.length) || running) return;`（`chat.js:662`）
- `setRunning()`：`sendEl.disabled = on;`（`chat.js:463`）

于是 run 在飞时输入框能打字，回车和 send 都是静默 no-op。

后端没有这个限制，反而是**明确设计的插话**：`workspace/ai/src/registry.ts:577` 注释 "A steered prompt joins the run in flight"，`agent.isStreaming` 时走 `agent.prompt(text, { streamingBehavior: "steer" })`（`registry.ts:610`）；`/ai/ask` 不看 `sess.active`（`server.ts:145`）。搬迁前的 `aiSend()` 也没有 `running` 守卫（`84d52d0^:workspace/web/app.js:2274`），所以过去执行中发送就是插话。

### 2. Esc 停止：同一处监听第二次被删

`76de383` 刚把 `b6e5af7` 删掉的 pane 级 Esc 监听补回来（设计记录 `2610-30`），它的最后一层就是"停当前 run"。一个月后 `84d52d0` 把 `app.js` 那段整体删掉，`chat.js` 只留了 stop **按钮**（`chat.js:33`、`:721`），没有任何 `Escape` 监听。

后端 `/ai/stop` → `registry.stop` → `agent.abort()`（`registry.ts:627`）完好，所以按钮能停、Esc 不能。

### 3. ↑/↓ 历史：整组函数被删

`f79ba0c` 加过一整套（设计记录 `2610-19`）：`aiPromptHistory` / `aiHistoryRecord` / `aiHistorySeed` / `aiHistoryEnd` / `aiHistoryShow` / `aiHistoryUp` / `aiHistoryDown` / `aiCaretVisualLine`（可视行测量）+ `#ai-input-field` 上的 keydown 分支。`84d52d0` 把这些函数全部删除，现在的 keydown 只处理 `Enter`（`chat.js:713`），`replayHistory()` 也不再把 user 轮次收成列表。

有意思的是 `components/chat.css:442` 还留着 `.ai-input-mirror` 的样式 —— 组件当时是**打算**搬这套测量的，样式过来了、JS 没过来。

## 决策

1. **一处一改，都用组件自己的状态**。组件是一个会话一个元素（`id` 在 `wire()` 里定死），所以历史不再是 `Map<sessionId, …>`，就是一份 `{ items, cursor, draft }`；不需要外壳的 hub/tab 概念。
2. **执行中发送 = 插话，不排队**。去掉三处守卫；`ask()` 里区分「新开一轮」与「插话」：
   - 新开一轮：清 `bubble` / `thinking` / `tools`，`setRunning(true)`，`await ready`，POST 之后 `pump()`；
   - 插话：只关掉正在写的 assistant 段落（`bubble.flush()`，下一个 delta 从用户消息下面开始新段落）与 thinking 芯片，**不动 `running`、不清 `tools`**（正在跑的工具芯片要能被它自己的 `tool_execution_end` 收尾），POST 之后**不新起 pump**（原来的流就是这个 run 的流，插话不会让流关闭）。
   - 插话的 POST 失败只报错，不 `finish()` —— 否则一次失败的插话会把还在跑的 run 从界面上停掉。
3. **Esc = stop 按钮**。抽一个 `stopRun()`，按钮和 `Escape` 共用；`Escape` 只在 `running` 时接管（`preventDefault`），空闲时让给别处（页面、浏览器、IME）。
4. **历史列表 = 本页面发过的 + 会话记录里的**。发送时记录（`ask()` 里记，顺带覆盖问题卡的作答），`replayHistory()` 那趟遍历顺手把 user 文本轮次收进列表（本来就要拉 `session-detail`，不加请求、不加契约）。带图片的轮次两处都跳过：文本回填不回图片。
5. **多行规则照旧搬**：↑ 只在「输入为空或光标在第一个**渲染行**」时翻，↓ 只在浏览中接管；软换行的长行算多行。测量用镜像 div（`.ai-input-mirror` 的 CSS 已经在），因为 textarea 没有光标盒 API。
6. **有暂存图片时不翻历史**：回填纯文本会让 `[image]` token 与 `images` 队列失配。

## 范围外

- 不动 `contracts/` / `atoms/` / `edges/` / 后端：`/ai/ask` 的插话语义、`/ai/stop`、`/log/session-detail` 都是现成的。
- 不做排队发送（run 在飞时发第二遍仍然立刻作为 steer 交给模型，与过去一致）。
- 不修 shell（`app.js`）的 tab / launcher / `/resume` / `/new` 交互。
- 不重写 `development/testing/dev/case-core-web-input-history` 与 `case-core-web-chat-controls`：两个用例的 `Run` 脚本指着 `app.js` 时代的 DOM（`#ai-input-field`、`#ai-cmd`、`#newtab`、`/chat/<id>`、pane 布局），`84d52d0` 之后整体失效，与本次改动无关；按现在的 shell 重写它们是后续项（这两个文件此刻正被另一条工作改动 / 删除，更不该在这里动）。本次的行为覆盖由新增的组件级用例 `case-core-web-chat-composer` 负责。

## 方案

只改 `workspace/web/components/chat.js`：

1. `setRunning()` 不再 disable 发送键；`submit()` / `ask()` 去掉 `running` 守卫。
2. `ask()` 拆出新开一轮 / 插话两条路径（决策 2）。
3. `stopRun()` + `inputEl` 之外的一个 `window` `keydown`：`Escape` 且 `running` → `stopRun()`；`disconnectedCallback` 里摘掉（元素被移除时不留监听）。
4. 历史：`{ items, cursor, draft }` + `historyRecord/Seed/Show/Up/Down/End`，`ask()` 里记录（无图片块时，文本块拼起来），`replayHistory()` 里 seed；`input` 事件退出浏览；`historyShow` 端光标。
5. 镜像 div 与 `caretVisualLine()`：照 `84d52d0^` 的实现搬，作用域收到组件内。
6. `inputEl` 的 `keydown` 在 `Enter` 分支前加 ↑/↓ 分支（同 `84d52d0^` 的判定：无图片、非组词、无修饰键）。
7. 占位提示补一句 `Esc stop`。

## 测试

新增 `development/testing/dev/case-core-web-chat-composer/`（ports 9040）：一个自带的假 provider（`/tmp` 里的 Go fixture，按 `contracts/ai-stream.yaml` 的形状发事件，并且**能按住一个 run 不收工**）+ 真 `serve-web` 资产（`workspace/web` 原文件，页面是一个只有 `<engineer-chat>` 的探针页）。三条都断言用户能观察到的东西：

1. run 在飞时再发一条：输入框清空、两条用户气泡、stop 仍然显示、fixture 收到了两次 `/ai/ask`（第一次收工时 `stops == 0`），且插话的回复出现在屏幕上；
2. run 在飞时按 Esc：fixture 收到一次 `/ai/stop`，stop 收起、发送恢复；
3. 空闲时按 Esc：`/ai/stop` 计数不变；
4. ↑/↓：最新一条先回来、往回走、走到底给回草稿；多行草稿里 ↑ 只移动光标；软换行长行同理。

## 风险

- 插话时清 `bubble` 会让 pi 在 steer 之后继续发来的同一段文本落进新气泡 —— 顺序正确（在用户消息下面），但与模型端「同一轮」的边界不完全一致，可接受。
- `stopRun()` 沿用按钮的乐观收尾（POST 后立即 `finish()`），不等待 `agent_settled` —— 与现有按钮行为一致，不引入两种手感。
