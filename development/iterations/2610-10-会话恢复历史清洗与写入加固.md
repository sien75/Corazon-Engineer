# 会话恢复历史清洗与写入加固

## 需求

修「记录持久化静默失败 → 会话永久损坏」这条链路。分两个独立改动，写入侧止血、读取侧兜底：

1. **写入侧**：`recorder.record()` 的 fire-and-forget 不再静默吞掉失败——检查 HTTP 状态码，
   瞬时失败带退避重试，最终失败明确上报，而不是 `.catch(() => {})`。
2. **读取侧**：`resume` 重建上下文前清洗历史——丢掉孤儿 `toolResult`、给没有结果的
   `toolCall` 补占位、按 `seq` 去重。一条坏记录不再把整个 session 卡死。

## 现状

链条（已逐条核对代码）：

- **写入无检测、无重试**：`workspace/ai/src/recorder.ts:51-59`，`fetch(...).then(r => r.text()).catch(() => {})`，
  不看 `res.ok`、不重试。写失败完全无声。
- **seq 先分配后写**：`workspace/ai/src/registry.ts:699` 的 `++sess.recordSeq` 在 `record()` 之前，
  写丢了号也不回收 → 记录里永久留 seq 空洞。`resume` 侧只用 `seq` 取 max 当下一个号段
  （`registry.ts:337`），对空洞无感。
- **resume 不做任何清洗**：`registry.resume()`（`registry.ts:315-322`）读全部记录直接
  `build()`；`build()`（`registry.ts:340-352`）只有两处「过滤」——
  - `history.slice(lastCompactionIndex(history))`：为压缩语义按**数组下标**切，不认消息配对，
    切点落在 assistant 与它的 toolResult 之间时会**自己造出新的孤儿**；
  - `toAgentMessage()` 对带 `raw` 的行**原样返回**（`registry.ts:415-427`），只有无 `raw` 的
    legacy 行才可能返回 `undefined`；`if (msg) appendMessage(msg)` 仅跳过 `undefined`。
  没有按配对校验、没有去重、没有重排。
- **pi 也不兜底**：`convertToLlm` 对 user / assistant / toolResult 原样透传
  （`node_modules/@earendil-works/pi-coding-agent/dist/core/messages.js:111-114`），
  再由 provider 适配器映射成 `{ role: "tool", tool_call_id }`
  （`node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js:1076-1079`）。
  孤儿 tool 消息就这样直送 DeepSeek → `400 Messages with role 'tool' must be a response
  to a preceding message with 'tool_calls'`，且每次重放整段历史都必然复现，session 永久卡死。
- **log 写入无幂等键**：`workspace/log/internal/store/store.go:84-108`，`id` 服务端生成，
  同一 `(sessionId, seq)` 可重复插入。

消息结构（本方案依赖，已核对 `node_modules/@earendil-works/pi-ai/dist/types.d.ts`）：
`AssistantMessage.content[]` 里的 tool 调用块是 `{ type: "toolCall", id, name, arguments }`；
`ToolResultMessage` 是 `{ role: "toolResult", toolCallId, toolName, content, isError, timestamp }`。

## 方案

### A. 写入侧 —— `workspace/ai/src/recorder.ts`

`record()` 的签名与 fire-and-forget 语义不变（调用方靠它保持顺序，且日志不能阻塞对话），
内部换成「检查状态码 + 有界退避重试 + 最终上报」：

- 最多 `RECORD_ATTEMPTS = 3` 次尝试；第 2、3 次前分别等 200ms / 400ms。
- 每次拿到响应先看 `res.ok`：`ok` → 成功返回；**4xx 是确定性失败**（参数/契约问题），
  立即放弃不再重试；5xx 或 `fetch` 抛异常（连接被拒/重置）→ 重试。
- 仍要 `await res.text()` 把 body 读掉，否则连接无法复用。
- 重试耗尽后 `console.error` 一行，带 `sessionId` / `seq` / 实际尝试次数 / 原因；
  **不抛出、不阻塞**，聊天流程照旧。
- 重试在 `writeTail` 链**内部**串行进行，记录顺序不乱；代价是退避期间后续记录被延后，
  最多约 600ms（可接受，记录流本来就是串行的）。

重复写入的风险由读取侧兜（见 B 的「同 seq 去重」），**本次不改 log 服务、不加幂等键**——
避免为这个缺陷动第二个服务的数据写入语义。

### B. 读取侧 —— `workspace/ai/src/registry.ts`

新增纯函数 `sanitizeHistory(records: StoredRecord[])`，与 `lastCompactionIndex` 并列。
只处理带 `raw` 的行；无 `raw` 的 legacy 行没有 tool 结构，原样放行（其重建/丢弃逻辑仍归
`toAgentMessage`）。

按顺序做两趟（已按实现回填）：

1. **判重 + 数空洞**（第一趟，扫全量）：`seq > 0` 的行按 `seq` 保留第一条。正常流里 `seq`
   单调唯一，只有重试产生的重复行会撞号（A 的副作用在此被兜住）。`seq <= 0` 的 legacy 行
   跳过此步。同一趟在排序后的 seq 集合上累加缺口数 `holes`——这是「确实丢过记录」的
   唯一痕迹（号已发出、行没落库），只报不补。
2. **重建 tool 配对**（第二趟，按记录顺序）：assistant 的 `raw.content` 里 `type === "toolCall"`
   的 `id` 按出现顺序收集；它后面**连续的 toolResult 段**就是配对窗口（provider 要求的
   形状）；命中的原样保留，缺失的按调用顺序插占位
   `{ role: "toolResult", toolCallId, toolName, content: [{ type: "text", text: "[record lost: this tool call's result was never persisted]" }], isError: false, timestamp }`；
   窗口之外的 `toolResult`（没有前驱 assistant 认领，或 id 对不上任何调用）一律丢弃。
   补占位而不是把这些块从 assistant 里删掉：删块可能连带丢掉 assistant 的正文，而且改
   assistant 的 `content` 数组更容易踩到 pi 的内部结构；占位只存在内存里。

挂点：`build()` 里改成
`const context = sanitizeHistory(history.slice(lastCompactionIndex(history)));`
**必须在 compaction 切分之后**，否则切完又会造出新的孤儿。

- 有任何修复（或 `holes > 0`）时 `console.error` 一行汇总，键值形态便于用例断言：
  `engineer ai: history repair <id>: filled=<n> orphans=<n> duplicates=<n> holes=<n>`；
  每个动作另加 `dbg()` 一行（`drop-duplicate seq=` / `drop-orphan seq= toolCallId=` /
  `fill seq= toolCallId=`），便于 `ENGINEER_AI_DEBUG` 下追溯，也让用例不依赖模型
  就能断言清洗确实发生、且发生在正确位置（dbg 的调用顺序与消息入列顺序一一对应）。
  健康历史一行不打。
- **不回写 log**：缺失的内容无法重建，把占位行写进永久日志只会污染记录。清洗是纯内存的。

## 范围外

- 不改 `contracts/` 的形状：`/ai/resume` 的请求/响应字段不变（不把修复计数放进响应），
  `/log/mutation` 不加幂等键。仅在 `contracts/ai-resume.yaml` 的 `description` 里补一句
  「重放前会修复畸形历史（孤儿 tool 结果 / 无结果 tool 调用 / 重复 seq）」。
- 不改 `atoms/` `edges/`：接口与事件流不变。
- 不做「记录补写队列」：宕机期间已经丢掉的记录不会补回来。
- 不改前端：前端从 log 重放的历史里，孤儿消息和空洞仍然可见——界面显示滞后于模型上下文。
- 不改 log / static / web 服务。

## 验收

1. **坏历史不再卡死**：一条被手工构造成「assistant 带无结果的 toolCall + 孤儿 toolResult +
   重复 seq」的 session，`/ai/resume` 返回 200，随后 `/ai/ask` 正常返回 200 并流式产出回复，
   **不再出现 provider 的 400**（需要用真实 provider 才能复现 400；`--stub` 下断言到
   「清洗发生 + 不报错」这一层）。
2. **清洗可观**：ai 的日志里出现清洗报告——补了 1 个占位、丢了 2 个孤儿结果、
   去了 1 条重复 seq，数量与实际构造的畸形数据一致；健康 session resume 时**不出现**
   任何清洗日志（干净历史零改动）。
3. **配对完好**：健康的 `assistant(toolCall t2)` + `toolResult(t2)` 原样保留，
   且占位结果排在它所属 assistant 之后、按调用顺序。
4. **写入失败不再静默**：log 服务不可达时，ai 的日志里出现明确的
   `conversation record write failed` 一行（含 sessionId / seq / 尝试次数）。
5. **瞬时失败能自愈**：面对「前两次 500、第三次 200」的 log 端点，第 3 次尝试成功，
   记录最终落在 log 里（断言该端点被请求 3 次 + `/log/session-detail` 里能读到这条记录）。
6. **4xx 不重试**：log 返回 4xx 时只请求一次，不浪费退避。
7. **不回归**：`case-core-ai-flow` 全绿（新建 / ask / 流式 / resume / 记录 / 删除）。

### 负向对照（确认用例真的复现了原 bug）

把**同一份构造数据**改由改动前的 `engineer-ai` 二进制（已安装的
`~/.engineer/apps/current/bin/engineer-ai`）重放，得到：

```
400: {"message":"An assistant message with 'tool_calls' must be followed by tool
messages responding to each 'tool_call_id', The following tool_call_ids did not have
response messages: tc_ghost ...","type":"invalid_request_error"}
```

同一个 stream 的三个计数：**修复前 `text_delta=0` / `stopReason: error=1`；修复后 `1` / `0`**。

顺带纠正了原报告的一处描述：这个 400 在 ai 侧**不会变成 `error` 事件**，而是被 pi
包成一条 `content: []` + `stopReason: error` + `errorMessage` 的 assistant 消息——
这正好对应「界面看起来发了没反应」。而且这条空消息会被照常落库（`recordMessage`），
所以中过招的会话历史里会多一条 `content: []` / `stopReason: error` 的记录。已实测：
重建时带上这条空 assistant 消息，DeepSeek 照常接受（1 text_delta、0 stopReason error），
不需要额外处理。

清洗对重复 resume 是幂等的：同一会话多次 resume 报告完全一致
（`filled=1 orphans=2 duplicates=1 holes=0`），中途新增的正常记录也不产生误报。

## 影响面

- `workspace/ai/src/recorder.ts`：`RECORD_ATTEMPTS=3` / `RETRY_BACKOFF_MS=200`，
  `postRecord()` 检查状态码（4xx 不重试）并在 `writeTail` 内退避重试，失败汇总上报；
  已加「tail 永不 reject」的兜底，避免一次异常让整条记录流静默断掉。
- `workspace/ai/src/registry.ts`：新增 `sanitizeHistory()` / `toolCallsOf()` / `LOST_RESULT_TEXT`，
  `build()` 挂点改为 `sanitizeHistory(id, history.slice(lastCompactionIndex(history)))`。
- `contracts/ai-resume.yaml`：仅 `description` 补一句（形状不变）。`static/validate`：ok、0 error。
- 新增 `development/testing/dev/case-core-ai-recover/`。

## 未做（本次范围外，未变）
