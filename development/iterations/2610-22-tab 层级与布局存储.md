# tab 层级与布局存储（pane 拆分 · i1）

> 本需求分三步落地：**i1 tab 层级与布局存储**（本文，后端）→ i2 前端接 tab 层级（等价重构）→ i3 拆窗渲染 + 布局工具 + skill。
> i1 不改任何前端行为、不动 ai。

## 需求

引入 tab 层级：一个 tab 有一棵 **pane 树**（怎么布局），树里每个 pane 关联一个内容（哪个 chat / 哪个 blueprint）。

- 布局是 **tab 层级的状态**，不是 session 层级、也不挂在 conversation 记录上。
- key = `tabId`，**由后端生成**。
- 存 log 的 sqlite。
- 三个接口：建/写、读、列（recents 用，限 100）。

术语：**pane**（不用 window，JS 全局对象冲突）。内容两种：`chat` / `page`。

## 现状

- 布局概念不存在。一个 tab 等于一个 session（chat tab）或一个 blueprint iframe（page tab）。
- 前端 `openTabs`（`workspace/web/app.js`）存 localStorage，`tab_xxx` 是前端随机串。
- log 拥有 sqlite（`.engineer/engineer.db`），只有 `records` 一张表，`kind ∈ {test, telemetry, conversation}`；`/log/list` 列 session，100/页。
- ai 的 7 个接口全是 session 层级（`Registry.sessions: Map<sessionId, Sess>`）。
- `edges/` 里 `web-to-log`、`ai-to-log` 已存在，前端和 ai 都直连过 log。

## 决策

1. **布局是 tab 层级单值状态**，key = `tabId`。一个 tab 一条记录，改布局是覆盖同一条，不是追加。

2. **新建一张 `tabs` 表**，不复用 `records`。
   理由：`records` 是**记录流**（有时间线、进 `/log/query` / `/log/search`、会话列表按 `kind='conversation'` 统计）。布局是**按 key 的单值状态**，放进去会让查询与列表被污染，且每次改都新增一行、读还得取最新。

3. **三个接口放 log**：`/log/tab/mutation`、`/log/tab/detail`、`/log/tab/list`。
   理由：布局本身就是一次数据库读写，没有别的业务；前端已经直连 log（`/log/list`、`/log/session-detail`），ai 写 sqlite 也只经 log（`/log/mutation`），两条边都在——再包一层 `/ai/tab/*` 是纯转发。
   代价：“改布局只能由模型执行”变成一条**约定**而不是接口层强制：写入口有两个（前端建 tab 时写一次、ai 的工具）。约定写进 i2/i3 的验收。
   注：`/log/tab/*` 是本项目第一次用嵌套路径（现有全是一层，如 `/log/list`）。契约名跟随：`log-tab-mutation.yaml` / `log-tab-detail.yaml` / `log-tab-list.yaml`。

4. **log 不认识 tab 的“种类”**（chat / page），也不认识布局树的语义。新建哪种由**调用方自己构造初始布局**决定，`/log/tab/mutation` 只负责存。
   - chat tab：前端先 `/ai/new` 拿 sessionId，再 put `{ pane: { content: chat, id: <sessionId> } }`
   - page tab：put `{ pane: { content: page, id: <blueprint slug> } }`
   这样 log 保持“只会存”的哑服务。布局树的语义校验（≤6 pane、brief 只能叶子）由写入方做：ai 的工具（i3）写入前校验，前端读到非法树就退化成单 pane。

5. **布局树 schema 定死**：

```yaml
# 单 pane（默认）
layout:
  pane:
    content: chat            # chat | page
    id: s_3f2a...            # chat = sessionId；page = blueprint slug

# 拆分示例：左右两栏，右边是一列（上 page，下 brief）
layout:
  split: col                 # col = 左右排；row = 上下排
  children:
    - pane: { content: chat, id: s_3f2a... }
    - split: row
      weight: 2
      children:
        - pane: { content: page, id: my-blueprint }
        - pane: { content: chat, id: s_9c1b..., size: brief }
```

- `split`：`col`（左右）| `row`（上下）。方向语义写死在这里，不再改。
- `weight`：`1 | 2 | 3`，同层相对比例，默认 1。**不开放百分比**。
- `size`：`fill`（默认）| `brief`（矮窗，固定高度）。
- 约束：整树最多 **6 个 pane**；`brief` 只能是叶子。
- pane 的 `id` 就是内容 id（sessionId / blueprint slug），不做独立 pane id；**同一内容重复出现允许**（两个 panes 装同一个 blueprint 没问题）。

6. `tabId` 格式 `t_<hex>`，与现有 `s_<hex>` 一致。

## 方案

### log：store

`workspace/log/internal/store/store.go`

```go
CREATE TABLE IF NOT EXISTS tabs (
  tab_id     TEXT PRIMARY KEY,
  layout     TEXT NOT NULL,   -- yaml
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
)
```

- `UpsertTab(tabID, layout Text) (Tab, error)`：tabID 为空时生成 `t_<hex>`；同 id 覆盖（保留 created_at）。
- `GetTab(tabID) (Tab, error)`：不存在返回 `sql.ErrNoRows`。
- `ListTabs(pageNum int) ([]Tab, bool, error)`：按 `updated_at DESC`，沿用 `PageSize = 100` + `hasMore` 的既有写法。

### log：server

`workspace/log/internal/server/server.go` 加三个 handler：

| 路由 | 入参 | 出参 |
|---|---|---|
| `POST /log/tab/mutation` | `tabId?`, `layout` (必填) | `{tabId, layout, createdAt, updatedAt}` |
| `POST /log/tab/detail` | `tabId` | `{tabId, layout, createdAt, updatedAt}`；无 → 404 `not_found` |
| `POST /log/tab/list` | `pageNum?` | `{tabs: [{tabId, layout, updatedAt}], pageNum, pageSize, hasMore}` |

- `layout` 用 yaml 文本存、原样返回（log 不解析树结构，不做语义校验；只校验非空）。
- `tabId` 缺失时 `/log/tab/mutation` 生成、`/log/tab/detail` 返回 400。
- 命名跟随 `/log/mutation` 的 `op` 风格可以后续再收，本 iteration 就用上面三个路由。

### 契约与静态关系

- 新增 3 个契约：`log-tab-mutation.yaml`、`log-tab-detail.yaml`、`log-tab-list.yaml`（照 `log-list.yaml` / `log-mutation.yaml` 的写法，request / response 写全）。
- `atoms/log.yaml` 的 `provides` 加三条，`extend.path` 如上。
- `edges/`：**i1 不加边**。validate 要求边的 `from_interface` 出现在消费方 atom 的 `consumes` 里，而 i1 不动 `atoms/ai.yaml` / `atoms/web.yaml`；硬加会声称一个还不存在的调用。消费方边随各自 iteration 加：i2 加 web 的，i3 加 ai 的。
- `atoms/ai.yaml`、`atoms/web.yaml`、`workspace/ai`、`workspace/web` **不动**（i2 / i3 才动）。

### docs

`docs/log.md` 补三个接口（生成方式见 `how-to/`）。

### 本 iteration 不动的

ai 源码、web 源码、任何前端行为。

## 测试

`development/testing/dev/case-core-log-tab/`（`desp.yaml` + `TEST.md`）：

1. `/log/tab/mutation` 不带 tabId → 拿到生成的 `t_...` 和新布局；
2. 带同一 tabId 再 mutation → `updatedAt` 变、`createdAt` 不变、`/log/tab/list` 里仍是一条；
3. `/log/tab/detail` 取回，与写入的布局逐字段相等；
4. `/log/tab/detail` 一个不存在的 id → 404；
5. `/log/tab/mutation` 缺 `layout` → 400；
6. `/log/tab/list` 的 `pageSize` 是 100；
7. 重启 log 后数据仍在（sqlite 落盘）。

## 范围外

- 前端不接（i2）：recents 改列 tab、page tab 走 tab 记录、旧 tab 补建 tabId。
- 拆窗渲染、per-pane 重构（i3）。
- 布局工具、skill（i3）。
- 每轮注入布局 —— **已明确不做**：不碰 system prompt、不碰 user 文本，模型想知道布局自己调工具读。
- 布局树的服务端语义校验（先信任写入方，最多校验非空）。
