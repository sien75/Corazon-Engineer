# E2E 用例修复与端口独占

> 由 i3（`2610-24-拆窗渲染与布局工具.md`）的回归引出来：跑既有用例时发现它们**本来就在失败**，追下去发现根因不是代码，是用例编排。

## 需求

让 `development/testing/dev/` 下的用例真的能当回归信号用，并把"怎么跑、怎么不互相踩"写成一份统一说明。

## 现状（修之前）

- 20 个用例里，多个**共用端口**：`8521`/`8522`/`8523`/`8524` 被 ai-recover、chat-route、page 三个用例共用；`8511`/`8513`/`8514` 被 input-grow 与 tabs 共用；`8610` 被三个用例共用，等等。
- 四个用例共用同一个 root `.engineer/.skill-test`。
- Setup 里**没有回收上一次的进程**（只有 Teardown 的 pkill，跑第二次之前没人清）。
- 后果：上一个用例的服务还占着端口 → 本次的服务 `EADDRINUSE` 起不来（错误埋在日志里）→ 前端连到**上一个用例的服务**、读**上一个用例的数据库**。表现是"答案不对"，不是"服务挂了"，极难查。
- 没有统一说明：怎么跑用例、setup/run/teardown 的形状、端口规则，全靠读各个 `TEST.md` 自己悟。

## 决策

1. **每个用例一套独占端口**，按用例名排序分配 `8800+10*i` 的连续块。谁都不和谁撞。
2. **每个 root 独占**：原来四个用例共用 `.engineer/.skill-test`，拆成 `.skill-crud` / `.skill-suggest` / `.input-grow` / `.tabs`。
3. **Setup 开头先回收**：按本用例的 root 和自己的端口 `pkill`，再启动。放在 Setup 里而不是只写在 Teardown —— 失败中断时 Teardown 根本不会跑到。
4. **fixture 同样回收**：`case-core-web-tool-chips` 自带一个假 provider 进程，它占的端口也要先清（否则新 fixture 起不来，跑的还是旧脚本）。
5. **写一份统一说明** `development/testing/README.md`：怎么跑、三段结构、端口与回收规则、什么算用例、什么不算。

## 方案

- `development/testing/README.md`（新）：用例的运行方式与规则。`development/README.md` 里加一句指向它。
- 19 个 `TEST.md`：端口重映射 + root 去重 + Setup 开头插入回收块。

## 顺带修掉的用例缺陷

跑起来之后暴露的真问题，分三类（**都已修**）：

**A. 用例自己的期望过期了**

- `case-core-web-tabs`：点返回后只等 URL 变就断言 DOM（竞态）；紧接着又多点一次 `.newtab-back`（那一瞬间还在子页才存在，靠竞态侥幸生效）；第 9 步跑技能开的**是空会话**（技能文本只在输入框里没发出去），却断言 reload 后有消息。
- `case-core-web-page`：还在断言 blueprint 报 `ai=...`，而 blueprint 早就改成 `static=...` + 调 `/static/query`；"recent 里不该有 page" 是 session 语义下的期望，tab 语义下**关掉的 page tab 本来就该出现在 recent**。
- `case-core-web-tool-chips`：还在用早已改名的 `.skill-item` 选择器；"recent 里重新打开会话" 也是 session 语义。

**B. 用例描述的意图，代码没实现**

- chip 对 `.agents/skills/<slug>/SKILL.md` 应显示 **slug + skill 图标**（`AI_ICONS` 里 `save_skill` 一直没人用）。已在 `aiToolChip` 补上。

**C. i3 引出的真 bug（前端）**

- 先设 `iframe.src` 才挂 `load` 监听 → 命中缓存时主题推不进去。
- 新标签页也会走 `/ai/resume`（以前 fresh 标签直接开流）→ 重放了历史，技能 tab 的实时流被污染。
- `rebindActiveTab` 在 replay **之后**清空消息列表 → `/resume` 换绑后对话是空的。

**D. fixture 跟不上**

- `case-core-web-tool-chips` 的假 provider 没有 `/log/tab/*`，也没有在 `/ai/new`、`/ai/resume` 里回 `tabId`。补齐三个端点。

## 补记：回收块把宿主服务杀了（我自己的 bug）

写完上面的修复后，宿主的 log / static （本项目 `.engineer/` 下、7502/7503）被我杀了，ai 服务开始刷 `log unreachable`。

**原因**：回收块是 `pkill -f "serve-log --root $ROOT"`。有 5 个用例的回收块被插在了 `ROOT=` **之前**（三个 static 用例与 web-serve、tool-chips 根本不用 `$ROOT` 这个变量），于是 `$ROOT` 展开为空，模式退化成 `serve-log --root ` —— **匹配全机器所有 log / static**。扫到 tool-chips 时就把它带上了。

**修法**（两层）：

1. 那 5 个用例改成各自真实的口径：三个 static 用 `$PWD/.engineer/.playground`；web-serve 和 tool-chips 只保留自己真会启的服务的回收（一个只跑 `serve-web`，一个只有 fixture + `serve-web`）。
2. 所有回收块开头加空变量守卫：`: "${ROOT:?this case must set ROOT before reclaiming}"` —— 宁可当场报错，也不要静默地把整台机器的服务杀光。规则写进了 `development/testing/README.md`。

**恢复**：只有 log / static 死了；**跑 agent 的 ai 进程（7501）从未被杀**，所以对话没断——它调用模型不经本地 log/static，只写记录时依赖 log。用安装版二进制按原参数手工拉起了两个服务，四个端口恢复。副作用：那段时间的对话记录没写进 log。

复验：tool-chips 32/32、page 15/15、tabs 41/41；三个 static 用例与 web-serve 手跑正常；每次跑完宿主 7500–7503 四个端口都在。

## 范围外

- 纯 curl 的用例（static / skill / blueprint 等）没有断言机制，只能人读；这次只保证它们**能起来**，没有逐个核对期望。给它们加断言是另一件事。
- `.engineer/.playground` 仍被多个 static 用例共用（一份只读 fixture 的副本）。有回收块之后不会互相踩，但并行跑仍会。

## 验收

- 九个浏览器用例连续跑全绿，无需人工清理进程。
- `static validate` `ok: true`。
