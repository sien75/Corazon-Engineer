# tab 先行:tabId 入参,布局 id 句柄化

> 由 i3（`2610-24-拆窗渲染与布局工具.md`）试跑时暴露的两件事:一个真 bug、一个顺序错位。

## 需求

1. **tab 先建,再往里放东西。** 拿到 tabId 之后才创建它的对话 —— tabId 是入参,不是返回值。
2. **chat pane 的 `id` 是句柄**:工具发、模型还。模型给了工具没发过的 id 要**报错**,不能悄悄换一个。
3. **`op=read` / `op=write` 显式化**,并把"涉及布局必先读"写进工具说明和 skill。
4. **前端在写入成功后才画**,画的是**工具返回的那棵树**。

## 现状(改之前)

- `/ai/new` 不带参数调用:ai 自己发一个 `t_a1ee…`,**前端又让 log 发一个 `t_6327…`** → 一个 tab 两条记录。
- 后果:模型 `layout op=read` 读的是 ai 那一条(空的),它看不到这个 tab 原来的 session id,于是**把用户正在进行的对话丢掉了**——试跑时表现为"拆窗后左边变成空对话"。
- 模型编 UUID 当 chat pane 的 `id`;`normalizeLayout` 只在 id 为空时才开会话,于是照单全收。
- 工具是"省参数=读、给参数=写";说明里没写 id 从哪来。
- 前端在 `tool_execution_start` 就按 **args** 画 —— 工具还没校验完,屏幕已经画了。

## 决策

### 修正:关联在 tab 上,不在对话上

初稿把 tabId 当成 session 的属性(`Sess.tabId`,由 `/ai/new`、`/ai/resume` 入参并记住),还让 ai 顺手把绑定写进 tab 记录。**方向错了。**

正确的模型:

- **tab 引用对话**(tab 的 layout 里存 sessionId),不是对话属于 tab。
- 一个 tab 可以装**多段对话**;不同 tab 也可以引用**同一段对话**。
- 所以 session 那一侧**没有 tab 这个概念**。

由此:

1. `/ai/new` 只管开一段对话 —— **不带 tabId、也不记得 tab**。放在哪张 tab 上是 tab 的事(前端写 `/log/tab/mutation`)。
2. `/ai/resume {id}` 同理,去掉 tabId。
3. **布局工具要知道"哪张 tab"** —— 但对话可能在多张 tab 上同时展示,所以不能从 session 上取。**由每次请求带上来**:`/ai/ask {id, tabId, blocks}`,该轮里工具就对这张 tab 操作。同一段对话从另一张 tab 里问,工具自动作用于那张 —— 语义比"存在 session 上"更准。
4. `/ai/ask` 不带 tabId 时,工具明确报错:"这一轮没有 tab 在作用域内",而不是猜。
5. **tabId 只由 log 发**(`/log/tab/new`)。前端要新建 tab 时先拿号,再建对话,再写布局。

### 布局 id 句柄化

6. **`op: read | write` 显式**;`op=write` 必须有 `layout`。
7. **chat pane 的 `id` 是句柄**:工具发、模型还。解析不到(既不是活会话也无历史)→ **报错**,并列出**本 tab 当前有效的 id**。模型看到就能改对;也消掉了"编一个恰好撞上无关会话"的可能。
8. 说明与 skill 写清:id 从哪来、怎么还;**涉及布局必先读** —— 布局是 tab 级共享状态,另一个 pane 的会话也能改它。

### 前端只在写入成功后画

9. 改成在 `tool_execution_end` + `!isError` 时,用**工具返回的树**(`result.details.layout`)重画 —— **屏幕上看到的 == 记录里存的**;写入被拒时界面不变。

## 测试

- **九个浏览器用例连续跑**(不手动 kill):chat-route 20、chat-scroll 10、input-grow 8、input-history 20、page 15、panes 9、tab-records 16、tabs 41、tool-chips 32 —— 全过。
- `case-core-ai-flow` 手跑新形状:不带 `tabId` 的 `/ai/new` 与 `/ai/resume` 都是 **400**;`/log/tab/new` → `/ai/new {tabId}` → 记录里出现 `layout.pane.id = <sessionId>`;带 `tabId` 的 resume 200。
- `case-core-ai-recover` 启动块手跑:log 200、三个 ai 200。
- `static validate` `ok = true`。
- **端到端(真模型)**:两句对话 → 让它"拆成左右两栏、左边别丢" → 拆完左边 **8 → 16 条消息**(对话保住),记录**只有一条**、`tabId` 前后一致。

## 顺带修掉的用例问题

- 回收块的 ai 模式 `main.ts --root $ROOT` 要求两者相邻,而 `case-core-ai-flow` 的实际命令是 `main.ts --bind … --port … --root …` → **在跑的 ai 从来没被回收到**。已统一改成 `main.ts.*--root $ROOT`(13 个文件),并把残留在跑的 9 个旧 ai 进程清掉。
- `case-core-web-tool-chips` 的假 provider:`/log/tab/detail` 永远返回 history 那条,导致 live tab 被当成 history。改成**真的存一份**(`/log/tab/new` 建空记录、`/ai/new` 填绑定),并补上 `/log/tab/new`。

## 补记:试跑又抓到的两件事

### 1. 两个 chat pane 时,点一个另一个掉样式（已修）

`style.css` 里 `#ai-messages { padding / font-size / line-height / display:flex / gap }` 是**按 id** 写的。而 tab 内只有**聚焦**的那个 pane 带 `#ai-messages`（未聚焦的只剩 class），于是点谁谁有内边距和 8px 间距，另一个被剥光。

改成 `.ai-messages`（class 每个 pane 都有）。id 仍然只在聚焦 pane 上 —— 那是给"当前对话"这类单例选择器用的，不是样式。

用例补了两条断言：两个 pane 的消息列表计算样式必须一致，且**切换焦点后仍然一致**（这正是坏掉的地方）。

### 2. 深链会为同一个 session 多建一条 tab 记录（**未修，待定**）

`/chat/<sid>` 打开一个**已经属于某张 tab** 的会话时，前端在 `openTabs` 里找不到它 → `openTab` → `syncTabRecord` 发现没有 tabId → **又建了一条记录**，并把 session 重绑过去。旧记录还指向同一个 session，于是 launcher 的 recent 里会出现两行。

实测：深链前 35 条记录，深链后 36 条。

这是 i2 引入的（在此之前前端没有 tab 记录可重复）。两个修法：

- **`/ai/resume` 回带它已有的 tab**（ai 的 `Sess.tabId` 就是它）→ 前端采用。仅对"活会话"有效，从历史重建的那种 ai 也不知道。
- **加一个按 session 找 tab 的查询**（`log-tab-find {sessionId}`）→ 都能覆盖，多一个契约。

## 补记二:每个 pane 自己的 composer（已在 2610-27 修正）

初稿的设计决策 2 写的是"composer 是单例,跟着焦点搬家",理由是"a textarea 不能同时在两处" —— 那是**实现取舍冒充设计**,后果就是"点哪个 pane 哪个才有输入框"。

改法是回到本来就该是的形状:**chat pane 就是原来的对话视图**(消息列表 + 输入框),每个 pane 一份。见 `2610-27-每个 pane 自己的 composer.md`。

## 范围外

- 关掉 tab 删除记录、拖拽改布局、重排时保住 chat 滚动位置 —— 同 i3。
- `/ai/ask`、`/ai/stream` 不带 tabId:它们作用于 session,不需要。

## 验收

- 上述测试全过。
- 一个 tab 只有一条记录;模型读到的 session id 与前端显示的一致。
